# Playground

Закрытая платформа для трёх разработчиков. Текущий этап: M4 — сборка, публикация и запуск игр. Работают аккаунты, библиотека, обсуждения, публичный GitHub/main, изолированные Docker-сборки, журнал, защищённый запуск и откат. VPS-развёртывание и Vault — следующие этапы.

## Локальный запуск

Нужны Node.js 22.13+, pnpm 10.34.5 и запущенный Docker Desktop с Linux-контейнерами (на Linux — Docker Engine). Если pnpm отсутствует, используйте `npx --yes pnpm@10.34.5` вместо `pnpm`.

```powershell
npx --yes pnpm@10.34.5 install --frozen-lockfile
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
npx --yes pnpm@10.34.5 dev
```

В Linux создайте `.env` из примера только если его ещё нет. Адрес: http://127.0.0.1:5173. API: http://127.0.0.1:3001/api/health. `dev` запускает API, frontend и отдельный worker. Игровые файлы обслуживаются на http://127.0.0.2:3003 — другом хосте, куда cookies портала не отправляются. Только локальный доступ. Ctrl+C останавливает процессы. Во время сна или выключения ноутбука приложение недоступно. Фонового опроса GitHub нет.

Если старый `dev` уже запущен, можно отдельно запустить сборщик в другом терминале: `npx --yes pnpm@10.34.5 worker`. Второй worker ожидает в standby, пока первый активен. При первом запуске сборщик подготовит доверенный Node.js Docker-образ; это требует интернета. В простое одноразовых контейнеров нет.

Данные хранятся в `data/database/playground.sqlite`, вне Git. DATABASE_PATH в `.env` задаётся относительно корня проекта или абсолютным путём. Миграции применяются автоматически при старте, транзакционно и однократно. Ручной запуск: `pnpm db:migrate`.

## Первый администратор

В отдельном интерактивном терминале из корня проекта:

```text
npx --yes pnpm@10.34.5 admin:create
```

Команда спросит имя и дважды пароль (вместо символов видны звёздочки). Минимальная длина пароля — 12 символов, максимальная — 128. Если поле заполнено неверно, команда объяснит причину и даст исправить это поле без перезапуска. Пароль не передаётся в аргументах команды, не сохраняется в Git и не выводится в лог. Команда работает только до создания первого пользователя. Дефолтного пароля и публичной регистрации нет.

Обновите страницу и войдите. При первом входе обязательно замените начальный пароль. В разделе **Команда** администратор может создавать аккаунты, менять роль, отключать пользователей, сбрасывать пароли, завершать сессии и назначать доступ к отдельным играм и права Vault. Новый аккаунт по умолчанию не имеет доступа к играм и Vault; администратор имеет полный доступ. После сброса пароля снова требуется его смена.

Тестовые игры и пользователи из автоматических тестов не попадают в рабочую базу.

Используйте адрес **http://127.0.0.1:5173**, а не localhost: разрешённый origin задан в `.env` через `APP_ORIGIN`. При смене адреса поменяйте и APP_ORIGIN (без завершающего `/`). Подробности безопасности: [docs/authentication.md](docs/authentication.md).

## Игры и обсуждения

1. В библиотеке нажмите **Добавить игру** или откройте **Игры → Добавить игру**.
2. Задайте название, короткий адрес страницы (например, `needle`) и описание. Это создаст страницу `#/games/needle`. Сохраните карточку; ссылку на GitHub можно подключить ниже, отдельно от короткого адреса страницы.
3. Загрузите обложку PNG/JPEG/WebP: до 5 МиБ и 16 мегапикселей, без анимации. Сервер проверяет файл и преобразует его в WebP. SVG и внешние URL не поддерживаются.
4. В **Команда** выберите коллегу и назначьте доступ к игре. Администраторы видят все игры.
5. Откройте страницу игры для обсуждения. Admin и Tester могут писать комментарии и редактировать свои; Viewer — только читать. Лимит: 4000 символов и 10 записей/правок в минуту на пользователя, суммарно по всем играм. Комментарии выводятся страницами по 20.

Администратор может скрыть комментарий, включить **Показать скрытые** и восстановить его. Чужой текст нельзя редактировать даже администратору. Смена отображаемого имени не меняет владельца комментария.

**В архив** скрывает игру от команды, сохраняя обложку, обсуждение и назначенные права. Из раздела **Игры** можно вернуть её в библиотеку. В архиве нельзя публиковать или редактировать комментарии. Изменение названия/адреса игры сохраняет обсуждение по постоянному ID.

Обложки хранятся в SQLite вместе с метаданными; при переносе базы они переносятся автоматически. Готовые игровые версии хранятся отдельно в `data/builds/releases`. Подробности карточек и комментариев: [docs/games-and-comments.md](docs/games-and-comments.md).

## Подключение публичного GitHub-репозитория

1. Откройте **Игры → нужная игра → Исходники на GitHub**.
2. Вставьте ссылку вида `https://github.com/owner/repository` и нажмите **Подключить репозиторий**. Поддерживаются также ссылки с `.git` и завершающим `/`.
3. Playground проверит публичность репозитория и наличие ветки **main**, сохранит последний коммит и время проверки.
4. Нажимайте **Проверить обновления**, когда нужно повторно прочитать main. Открытие страницы и перезапуск сервера сами GitHub не опрашивают.

Ключи, GitHub App и токены сейчас не нужны. Приватные репозитории и другие ветки отложены по решению владельца. Если main отсутствует, переименуйте нужную ветку в GitHub или используйте репозиторий с main.

Статусы последнего и опубликованного коммита разделены. До первой успешной сборки отображается **«Версия найдена · ещё не опубликована»**; сама проверка обновлений не скачивает исходники и не публикует игру. При ошибке GitHub сохраняется предыдущая успешная проверка. Отключение репозитория сохраняет карточку, обложку, опубликованную игру и обсуждение.

## Собрать, опубликовать и играть

1. Запустите Docker Desktop. В редакторе подключённой игры нажмите **Проверить обновления**.
2. В блоке **Сборка и публикация** оставьте **Папка проекта** равной `.`. Для единственной вложенной игры папка находится автоматически; для needle также можно явно указать `needle-in-a-haystack`.
3. Нажмите **Собрать и опубликовать**. Сохраняется задание с конкретным показанным SHA из main. Выполняется одна сборка за раз; страницу можно закрыть.
4. Журнал и статус обновляются автоматически, пока сборка активна. При успехе открывайте страницу игры и нажимайте **Играть**. Есть полноэкранный режим и открытие отдельно.
5. Для обновления: push в main → **Проверить обновления** → **Собрать и опубликовать**. GitHub Release или тег не нужны.

При ошибке сборки опубликованная версия остаётся доступной. В **Сохранённые версии** можно откатиться без повторной сборки. Комментарии не зависят от версии. Прерванные работающие задания при перезапуске worker отмечаются ошибкой; задания в очереди сохраняются.

Текущий preset: Node.js 22, npm ci или pnpm с lockfile, `build` script, выход `dist/index.html`, относительный Vite base (`--base=./`). Установка зависимостей выполняется без lifecycle scripts через разрешённый npm registry proxy; непосредственно сборка — без сети. Исходный GitHub-репозиторий не меняется. Custom .npmrc, pnpm hooks/workspaces и зависимости вне npm registry в этом preset не поддерживаются.

Игровой доступ выдаётся на час, только к конкретной версии и только при действующей сессии/правах. Для обновления доступа нажмите **Перезапустить игру**. При выходе из портала, отключении аккаунта или отзыве прав новые запросы игровых файлов отклоняются. Файлы не раздаются публичным каталогом. Подробности лимитов и изоляции: [docs/build-isolation.md](docs/build-isolation.md).

Все успешные версии сохраняются. Перед сборкой требуется хотя бы 1 ГиБ свободного диска. Автоматическая очистка старых релизов пока не реализована.

Без авторизации GitHub разрешает до 60 REST-запросов в час на исходящий IP; одно подключение/проверка использует два запроса. При достижении лимита приложение предложит повторить позже. [Лимиты GitHub](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). Подробности реализации: [docs/github-public.md](docs/github-public.md).

## Проверки

```text
pnpm build
pnpm typecheck
pnpm lint
pnpm test
pnpm exec playwright install chromium
pnpm test:e2e
```

Серверные тесты проверяют API, миграции, сохранность данных, сессии/CSRF, права, обложки, комментарии, артефакты, публикацию/откат и доступ к каждому игровому файлу. Браузерные сценарии используют временную базу и отдельные порты 5174/3002/3004. Для установленного Edge можно не скачивать Chromium: в PowerShell задайте `$env:PLAYWRIGHT_CHANNEL = 'msedge'` перед `pnpm test:e2e`. Обычные браузерные тесты используют fixture worker; реальная Docker-сборка проверяется отдельно:

```powershell
npx --yes pnpm@10.34.5 --filter @playground/api exec tsx ../../infra/scripts/smoke-build.mts
npx --yes pnpm@10.34.5 --filter @playground/api exec tsx ../../infra/scripts/smoke-worker.mts
$env:PLAYWRIGHT_REAL_GAME = '1'
npx --yes pnpm@10.34.5 test:e2e
```

Smoke-команды явно собирают публичную needle и используют отдельные каталоги в `data/`, без изменения рабочей базы. Первый создаёт настоящий артефакт для браузерного теста; второй проходит API → очередь → настоящий worker → Docker → публикацию. Тест с `PLAYWRIGHT_REAL_GAME=1` проверяет WebGL, все файлы сборки, fullscreen и мобильную раскладку.

## Docker и будущий VPS

```text
docker compose up --build -d
docker compose logs -f
docker compose down
```

Нужен запущенный Docker Engine. Адрес: http://127.0.0.1:8080. API не публикует внешний порт. Данные сохраняются в volume `playground-data`; обычный `down` их сохраняет. Не запускайте `down -v`, если данные нужны. Docker задаёт окружение явно и не использует локальный `.env`.

Compose сейчас настраивает портал и выдачу уже существующих игровых файлов (отдельный адрес http://127.0.0.2:8081). Worker намеренно не получает Docker socket внутри API/игровых контейнеров. Полная работа сборок проверена для нативного запуска `pnpm dev` + Docker; Compose/VPS-связка с host worker и общим хранилищем относится к M5. Не смешивайте нативную базу `data/` и отдельный named volume Compose.

Первого администратора внутри Docker создайте через `docker compose exec api pnpm --filter @playground/api admin:create` (интерактивный терминал обязателен). Эта локальная Compose-конфигурация намеренно использует development и HTTP на loopback. Для VPS нужны отдельная HTTPS-конфигурация, `NODE_ENV=production` и реальный `APP_ORIGIN` с HTTPS. При production сервер отклоняет HTTP-origin и устанавливает Secure cookies.

Для переноса остановите API и worker и скопируйте весь каталог данных (для Docker — содержимое volume) на целевой сервер: SQLite вместе с `builds/releases`, а позднее и Vault. Не копируйте только SQLite-файл работающей базы: актуальные данные могут находиться в WAL. Резервную копию храните также на другом устройстве. Секреты настраиваются отдельно и не попадают в Git.

Текущая конфигурация предназначена только для локальной разработки. До открытия в интернет нужны HTTPS, отдельный origin игр, утверждённая изоляция сборок и проверенные резервные копии. Провайдер, домен и GitHub App пока не настроены.

Требования: [AGENTS.md](AGENTS.md), [DESIGN_AND_VAULT.md](DESIGN_AND_VAULT.md). Актуальный масштаб: три разработчика, допустимы медленные последовательные сборки, сначала ноутбук, затем возможен VPS.
